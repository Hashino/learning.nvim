# demo/

Tooling that records the README demo GIF automatically with
[VHS](https://github.com/charmbracelet/vhs), so it can be regenerated instead of
hand-made.

## Files

| File | Purpose |
|------|---------|
| `record.sh` | One command: reset the demo file → record → convert → write `demo/demo.gif`. |
| `demo.tape` | The VHS script driving the recorded session. |
| `init.lua`  | Minimal headless config nvim is launched with (provider from env, fallback). |
| `demo.c`     | The file opened in the demo (reset by `record.sh` each run). |
| `demo.gif`  | The generated output the README embeds (produced by `record.sh`). |

## Regenerating the GIF

```sh
export LEARNING_API_KEY=sk_...
./demo/record.sh
```

`record.sh` moves aside `~/.local/share/nvim/learning.nvim` so recordings start from a clean "beginner" state.

`record.sh`:

1. **resets** `demo/demo.c` to its canonical one-function state (so an
   interrupted/saved previous run never leaves stale content);
2. **records** `demo.tape` with VHS to `demo.mp4`;
3. **converts** the MP4 to `demo/demo.gif` with ffmpeg.

Tunable via env: `OUT` (default `demo/demo.gif`), `WIDTH` (1280), `FPS` (15),
`LEARNING_API_URL` / `LEARNING_MODEL` (default to mercury), `KEEP_MP4=1` to keep
the intermediate `demo.mp4`.

### Provider / API key

The key is **never committed** (this dir is in the repo). `init.lua` reads the
provider from the environment:

- if `LEARNING_API_URL`, `LEARNING_API_KEY`, and `LEARNING_MODEL` are all set,
  that provider is used (`record.sh` defaults the URL+model to mercury and
  requires only the key from your environment);
- otherwise it falls back to the free, keyless `nemotron` provider the tests
  use, so the demo still runs out of the box (just slower — the tape's sleeps
  are tuned for mercury's ~1–2 s latency).

## What the tape records

1. Open `demo.c` (already contains an idiomatic `sum()`).
2. Add a second function with a blatantly non-idiomatic pattern — an `if`-guard
   returning one of two values where a ternary says it all.
3. The live suggestion window appears; press the **learn** key (`Ctrl+L`) to
   enter the drill (the reference is commented out).
4. **Fail on purpose**: re-type the branchy version and submit (`Ctrl+S`) — the
   scaffold escalates to a closer worked example.
5. **Pass**: collapse the body into `return a > b ? a : b;` and submit — the
   drill is mastered (the comment reference is dropped, the idiomatic code kept).
6. Move to the original `sum()` and run `:Learning explain` on a line to show the
   on-demand explanation window.
7. Dismiss and quit unsaved (so `demo.c` stays pristine).

## Notes / gotchas

- **MP4, not GIF, from VHS.** A demo that waits on a live AI several times runs
  long, and GIF palette encoding holds the whole frame sequence — a long
  high-res GIF can exhaust memory and silently produce a **0-byte** file (VHS
  doesn't check ffmpeg's exit code). Recording to MP4 (a streaming H.264 encode)
  avoids that; `record.sh` converts to GIF afterward with capped fps/scale.
- **Live AI is non-deterministic.** mercury chooses the lesson. The ternary
  example is biased so it reliably teaches one predictable thing the scripted
  answer fixes, but if a take doesn't trigger or teaches something off, just
  re-record (each take is ~50 s). The plugin's reliability tracking the model is
  expected — the README already notes results depend on model quality.
- **Sleeps, not `Wait`.** A VHS `Wait` timeout aborts the whole recording, and a
  live AI isn't guaranteed to print a given string, so the tape uses fixed
  `Sleep`s sized for mercury rather than content-driven `Wait`s.
- **`:Learning explain`, not the `<leader>le` mapping, in the tape.** The visual
  `<leader>le` mapping bails on the session's *first* visual selection
  (`utils.visual_selection` returns early when `vim.fn.visualmode()` is still
  empty). Invoking via `:` from visual mode sets the `'<`/`'>` marks, so the
  command form is reliable. (This is a latent plugin bug for first-use of the
  mapping, not specific to the demo.)

## Current state

- The full pipeline is implemented and verified end-to-end against live mercury:
  suggestion → learn → drill (fail → easier example → pass/master) → explain,
  producing a valid `demo.gif`.
- `init.lua`, `tests/init.lua`, and `tests/shared.lua` resolve paths from their
  own location, so everything works from any checkout / cwd.
- The README embeds `demo/demo.gif`; the old hand-made `demo1.gif`/`demo2.gif`
  were removed.
- `demo/demo.gif` itself is regenerated by running `record.sh` (see above).
